- 2026-08-10 — unit 0.12 CLOSED PENDING HUMAN BROWSER VERIFICATION (PR #221): a login trap on the product's first screen — after one mistyped password NextAuth parks the user on `/login?error=CredentialsSignin`, and from there a SUCCESSFUL sign-in was reported as a failure, so the account appeared locked while the server issued a session every time; the mechanism is NOT a redirect (we use `redirect: false` and never navigate) but a poisoned RETURN VALUE — next-auth/react's signIn defaults `redirectTo = callbackUrl ?? window.location.href`, POSTs that as `callbackUrl`, the server echoes it back as `data.url` on success, and signIn then parses `error` back out of it via `new URL(data.url).searchParams.get("error")`, so the stale param resurfaced as a fresh failure; fixed by passing an explicit `redirectTo` (canonical destination) so no query string makes the round trip, noting `res.ok` is unusable as a success signal because @auth/core answers 200 under X-Auth-Return-Redirect even for genuine failures, leaving `res.error` as the only discriminator; the same six lines also carried a POST-AUTH OPEN REDIRECT — the old `raw.startsWith("/") && raw !== "/"` guard accepted `//evil.example`, `/\evil.example` and TAB/LF/CR-smuggled variants that browsers strip before resolving — now allowlisted to same-origin app paths; A5 confirmed this `callbackUrl` was the ONLY user-supplied redirect target anywhere in the app, every other redirect being a hard-coded literal, a same-origin `url.pathname`, or a boolean flag to a server-generated presigned URL; the logic was extracted to src/lib/login-redirect.ts WITH THE DEFECT INTACT and typechecked first so T1 could be seen to fail against real production logic, and this entry stays PENDING until the browser sequence is reproduced by hand — mistype the password once, land on `?error=CredentialsSignin`, enter the correct password, confirm arrival at /dashboard with no stale banner, plus `/login?callbackUrl=//example.com` landing on our own /dashboard.
